# Decisions

- Repo at `C:\dev\salon` (outside OneDrive) — OneDrive syncing node_modules corrupts installs.
- Prisma pinned to 7.10.1 — npm `latest` is an 8.0 release candidate; 7.x is the stable line.
- TypeScript pinned to 5.9.3 — TS 7 (native) is brand new; tooling compatibility not guaranteed.
- Tailwind v4 CSS-first tokens (`theme.css`) instead of a JS preset — v4 no longer uses `tailwind.config` presets.
- Auth.js = `next-auth@5` beta (v4 `latest` is Pages-router-oriented). Beta risk noted; revisit in M5.
- pnpm 12 blocks dependency build scripts by default; allowlisted esbuild, workerd, unrs-resolver in `pnpm-workspace.yaml`.
- OpenNext build cannot run on this Windows machine without symlink permission; size checks run in GitHub Actions (Linux).
- Placeholder brand name/domain (`example.com`) until supplied.
- Schema written from the brief (reference `schema.prisma` was not supplied); lives at `packages/db/prisma/schema.prisma`.
- Instant columns (`startAt`, `endAt`, promo dates) are `timestamptz` — Prisma's default `timestamp` makes `tstzrange` non-immutable and breaks the exclusion constraint.
- Exclusion range is `[)` so end == next start is allowed; extra CHECK `endAt > startAt`.
- Prisma 7: datasource URL is in `prisma.config.ts` (DIRECT_URL for migrations, else DATABASE_URL); client uses a driver adapter (`neon` on Workers, `pg` locally/CI) — see `createDb`.
- Local Postgres on host port 5433 (avoids clashing with an existing local Postgres).
- Staff schedules: ISO weekday + minutes-since-midnight rows (multiple rows/day allowed for split shifts).
- A service is offered at a branch only if a `BranchService` row exists with `available = true`.
- `create-staff` prints a random one-time password and sets `mustChangePassword` (no password on the CLI, so none in shell history); `--reset` re-issues for an existing account.
- Password hashing: PBKDF2-SHA256, 100k iterations (workerd cap). CPU cost vs Free 10 ms cap to be measured on a deployed Worker in M5.
- Docker CLI is not on PATH in some shells: `C:\Users\elect\AppData\Local\Programs\DockerDesktop\resources\bin`.
- Staff app is served at `<domain>/admin` (option A): separate Worker with Next `basePath: '/admin'`, reached via a Cloudflare route `domain/admin*`; the website Worker serves everything else. Keeps a separate 3 MiB budget per Worker. Tradeoff vs a subdomain: same origin as the public site, so rely on strict CSP + short sessions + session cookie `Path=/admin`.
- Customers have no accounts or login anywhere; staff accounts only via CLI/OWNER/manager.
- Booking engine (`packages/booking`): core is pure TS behind a `BookingPort`; the Prisma implementation is a separate entry point (`@salon/booking/prisma`). Unit tests use an in-memory port; a second suite runs against real Postgres.
- Online slot starts are multiples of the grid (5 min) from branch-local midnight (not from opening time), so a shift starting at 10:02 first offers 10:05.
- Booking window is by branch-local calendar date: today through today + `windowDays` inclusive (not "now + N×24 h"). With the owner's 7 days, on Mon 2 Nov the last bookable date is Mon 9 Nov.
- Buffer is a minimum gap between a stylist's appointments, enforced in app code. `endAt` and `totalDurationMin` are the services only (what the customer is shown); the DB constraint sees raw intervals, so with buffer > 0 a simultaneous race could in theory leave a gap below the buffer. Default is 0.
- "Upcoming bookings per phone" counts PENDING + CONFIRMED appointments starting after now; applies to ONLINE only.
- Staff bookings (WALK_IN, PHONE) skip the public rules (slot grid, min notice, window, per-phone cap, no "past" check) so a walk-in can start right now at any minute. They still need opening hours, the stylist's shift, no time off and no overlap.
- Each create attempt is its own transaction: Postgres aborts a transaction after a failed statement, so the `ANY` retry (next-best stylist) needs a fresh one.
- Customer upsert never overwrites an existing name (public bookings must not rename someone else's record) and selects only `id` (`Customer.notes` is never read). The upsert touches `updatedAt` on purpose: the row lock serialises concurrent bookings by one phone so the cap cannot be beaten (verified by a test that fails without it).
- Lost races are `23P01` (exclusion violation) and also `40P01`/Prisma `P2034` (deadlock victim among overlapping inserts); all map to "slot taken". A per-stylist `pg_advisory_xact_lock` before the insert queues contenders so the loser gets an immediate 23P01 instead of waiting out `deadlock_timeout` (1 s). The exclusion constraint remains the final arbiter.
- `manageTokenHash` is the SHA-256 of a random 256-bit token; the token is discarded (v0 has no manage page).
- Phones: `libphonenumber-js/min` metadata (smaller Worker bundle), default country IN, stored as E.164.
- Postgres integration tests refuse any non-localhost database and create/delete their own uniquely named rows, so they are safe on the dev DB. In CI a missing `DATABASE_URL` is an error, so they can never be skipped silently.
- Owner-set booking rules (2026-11-01), replacing the brief defaults: 5 min slot grid (was 30; the owner wanted starts like 10:00, 10:10, 10:15, 10:20, all multiples of 5), 20 min minimum notice (was 120), 7-day window (was 60), max 2 upcoming online bookings per phone (was 3). Buffer stays 0. Staff walk-in/phone bookings deliberately stay exempt from grid, notice, window and cap: the owner said walk-ins and calls are handled by staff separately. Tests pin their own rule values (`test-support/rules.ts`); `defaults.test.ts` checks the live defaults.
- M3 website: every content page is prerendered at `next build` (all routes static, verified in the build output) and served with OpenNext's read-only `staticAssetsIncrementalCache`: no R2/KV/queue bindings, nothing to maintain. Consequence: a content change (price, promotion, hours) needs a redeploy. Time-based ISR would need an R2 bucket + Durable Object queue + self-reference binding (see FUTURE.md).
- The pages do NOT talk to the database. `apps/web/scripts/snapshot.ts` copies the content out of Postgres into `apps/web/src/generated/catalog.json` before every dev start, build and typecheck, and the pages read that file. So the deployed Worker carries no database code and needs no database at runtime. The build machine needs `DATABASE_URL` (`apps/web/.env.local` locally; CI migrates and seeds a Postgres service first).
- Measured on a Linux build (same as CI), website Worker gzip size: hello-world 840 KiB; M3 with Prisma + pg/neon drivers bundled 3,074 KiB (over the 3,072 KiB Free limit as the brief states it); M3 with the snapshot 1,095 KiB. Prisma and its drivers cost about 2.2 MiB gzipped, so the M4 booking API (which must reach the database at request time) needs a decision before it is built: see HANDOFF.md.
- Cloudflare docs conflict on the Worker size limit: the limits page fetched on 2026-11-01 says "There is no compressed size limit", 64 MiB uncompressed on both plans, and calls the gzip figure "for reference"; other Cloudflare pages and search results still say 3 MB (Free) / 10 MB (Paid) compressed. Unresolved until a real deploy. Free CPU time is 10 ms per request (Paid: 30 s default); that, not size, is the likelier problem for Prisma in a Worker.
- "Active promotions" are judged at build time (active flag + date range), so an expired offer stays on the page until the next deploy. A scheduled daily redeploy fixes this (add to DEPLOYMENT.md in M6).
- Services branch switcher: the static page embeds every branch's prices/durations and the switch happens in the browser. The choice is stored in cookie `salon_branch` (the branch slug; set by the browser, SameSite=Lax, 1 year, not httpOnly because it is not sensitive) for the booking flow to use as its default. Server HTML shows the first branch; a returning visitor's branch is applied on load.
- Branches are listed in creation order (no sort column in the schema yet), so the owner controls the order by the order they are added.
- "Open now" is computed in the browser from the branch's hours and timezone with `Intl` (no date library in the client bundle); the visitor's own timezone is ignored. Verified with a forced clock and a Los Angeles visitor.
- Fonts: Fraunces (display) + Inter (sans), self-hosted from npm via Fontsource (no build-time call to Google). Placeholder pairing, a one-line swap in `globals.css`.
- Not used in M3: shadcn/ui and Framer Motion. Plain Tailwind components and a CSS-only fade (disabled for `prefers-reduced-motion`) keep the client bundle and maintenance small.
- Images: `ImageSlot` uses `next/image` with `unoptimized` (there is no image optimiser on the Workers free plan), fixed aspect ratios so nothing shifts, lazy loading, and a decorative placeholder until real R2 photos exist. Upload photos already sized (about 1600 px wide).
- Branch map is a "Get directions" link (the branch's `mapUrl`, else its coordinates, else an address search), not an embedded map: no third-party iframe, simpler CSP.
- `/book` is a placeholder (branch phone numbers, noindex) until M4 builds the flow; the header, menu and sticky-bar buttons already point at it.
- Legal pages are placeholder copy with a visible "not legal advice, lawyer must review" notice; every fact I could not know (retention, grievance officer, payment terms, "we do not sell data") is a [bracketed] gap, not an invented statement.
- Mobile menu button keeps a constant name ("Menu") and reports state with `aria-expanded` (the standard disclosure pattern); the sticky bar is a labelled `nav` landmark.
- M4 database access: the owner chose (2026-11-01) to keep Prisma in the Worker and to be on Workers Paid (from $5 USD/month) at launch. The lighter-SQL alternative was dropped. Content pages still read the build-time snapshot; only the booking API touches the database at request time, with a Prisma client created lazily per request (`DB_DRIVER=pg` locally and in CI, the Neon driver by default on Workers). Linux build size with everything: 3,061 KiB gzipped.
- Booking API (apps/web/src/server): `GET /api/availability`, `GET /api/stylists`, `POST /api/bookings`. Handlers take every dependency as an argument so the security order is unit-tested without a database. Failures are `{ error: CODE }` with the engine's reason codes; the wording lives only in `lib/booking-copy.ts`.
- Defences on `POST /api/bookings`, cheapest first: same-origin check (Origin, else Referer, compared with Host) -> per-IP rate limit -> JSON only, at most 8 KB, strict Zod schema (unknown fields such as a price are refused, consent must be literally true) -> honeypot -> mobile number normalised -> Turnstile verified on the server -> per-phone rate limit -> the engine. The per-phone limit runs after Turnstile so a bot cannot burn a real person's allowance.
- Limits: 5 booking attempts per IP per minute, 3 per phone per hour, 60 reads per IP per minute (reads are limited much more loosely than writes, as the brief asks). Counters are fixed-window values in KV keyed by a SHA-256 of the IP or phone (no personal data in KV). If the counter store errors, the request is allowed and the error logged: a broken counter must not stop real customers. With no KV binding (local dev) an in-process store is used.
- KV caveat (verified in Cloudflare's docs 2026-11-01): eventually consistent (up to 60 s or more between locations), no atomic increment, one write per second per key. So the limits are a coarse brake, not an exact meter; Turnstile and the engine's per-phone cap of upcoming bookings back them up. Durable Objects are the upgrade if exactness is ever needed.
- Honeypot field is `company_website`. A filled honeypot is rejected like any bad input (400), not faked as a success, because browsers can auto-fill hidden fields and a real person must be able to retry.
- Turnstile: always verified on the server (the widget alone protects nothing); fails closed with 503 if the secret is missing or Cloudflare is unreachable. Tokens are single-use and last 5 minutes, so the widget is reset after every failed attempt. Dev and tests use Cloudflare's published dummy keys (they always pass); the real site key is inlined at build time and the real secret is a Worker secret.
- Phone numbers: the engine now uses libphonenumber's strict ("max") data and online bookings must be a MOBILE number. Found by the browser tests: with the small "min" data `1234567890` was accepted and booked, and even the strict data accepts it as a landline. Staff bookings (phone/walk-in) may still enter a landline. International mobiles with a country code are accepted.
- Confirmation page is client-only: the API returns the booking once, the browser keeps it in sessionStorage for that tab, and `/book/confirmation` reads it from there. There is deliberately no page that looks a booking up by id (no accounts, and an id in a URL would expose a customer's booking). Opened anywhere else it shows a friendly "we can't show your booking here, phone the branch" message.
- "Add to calendar" builds the .ics in the browser (UTC times, RFC 5545 escaping and folding, UID `<booking id>@salon-booking`, so re-adding updates rather than duplicates). Reference shown to customers is the last 8 characters of the booking id.
- Stylist choice is loaded live from the API (accurate, and the engine decides who is qualified for ALL chosen services), not from the build-time snapshot. The booking result now includes the stylist's name.
- Booking UI: five steps (branch, services, stylist, date and time, details), with the date as a row of day buttons (the window is only 7 days, so no calendar widget) and times grouped by hour. Changing an earlier choice clears later ones that no longer fit. Focus moves to each step's heading.
- Browser tests are committed (Playwright, 39 tests, run by `pnpm --filter @salon/web e2e` and by the CI `check` job): the full booking on desktop and phone with database checks and the .ics, two customers racing for one slot, validation, branch preselection, accessibility of every step, plus every public page at phone and desktop width. They need a seeded local Postgres, refuse non-local databases, and delete their test bookings (phones +919000000xx). Each test uses its own fake visitor address (x-forwarded-for) so the rate limit never mixes tests. They call Cloudflare's real Turnstile verification with the dummy secret, so they need internet.
- Sitemap now includes `/book`; `/book/confirmation` is noindex and not in the sitemap.
- M5 roles: OWNER every branch (book, change status, clients, team); BRANCH_MANAGER own branch (the same, plus the team of that branch); RECEPTIONIST own branch (view, book, change status, clients); STYLIST own appointments only and strictly read-only (no clients, no booking, no status changes, and no customer phone numbers: they see who is coming, not their number). The brief only said "own schedule only", so letting stylists complete their own appointments is in FUTURE.md.
- Who someone is, is always re-read from the database on every request (role, branch, still active). The session cookie holds only their id. So a deactivated or demoted person loses access at once, not when the cookie expires. Nothing the browser sends decides role or branch.
- Appointment queries ALWAYS start from `appointmentScope(actor)` (apps/staff/src/server/access.ts), so the database never returns a row the person may not see. Something that exists but is out of scope gives the same NOT_FOUND as something that does not exist, so the app never confirms that a record exists. Only `apps/staff/src/server/data.ts` talks to the database for staff features.
- Customers are visible to the front desk only if they have an appointment in that person's scope (owners see everyone); their visit history is limited to the same scope. `Customer.notes` is never selected. Client lookup is by part of the phone number (at least 4 digits).
- Status moves: CONFIRMED/PENDING -> CHECKED_IN, CANCELLED or NO_SHOW; CHECKED_IN -> COMPLETED or CANCELLED; finished appointments (COMPLETED, CANCELLED, NO_SHOW) stay finished (no reopening in v0). Cancel and no-show ask "are you sure?" first. The update only applies if the status is still what was read, so two people pressing different buttons at once cannot both win (the loser gets CONFLICT). Cancelled and no-show appointments free the stylist's time at once (the database overlap rule ignores them).
- Audit log: STATUS_CHANGE ({from, to}), CREATE_BOOKING ({source}), PASSWORD_RESET ({targetStaffId}), PASSWORD_CHANGE. Never contains a password, name or phone. Rescheduling is not built (no reschedule screen yet), so there is nothing to audit for it.
- Desk bookings use the same engine as the website (`source` WALK_IN or PHONE). They skip only the customer-facing rules (5-minute grid, minimum notice, 7-day window, per-phone cap, mobile-only), may start at any minute (even right now) and may use a landline. A new engine option `forStaff` lists free times the way the desk needs them: any date from today on, from the current moment, no notice.
- Auth.js: `next-auth@5.0.0-beta.32` (pinned; v5 is still a beta), credentials provider, JWT session, 8-hour sessions. Config is a function so settings are read per request (Workers variables are only available then). Cookie `salon-staff.session` (`__Secure-` prefix on https), HttpOnly, SameSite=Lax, Path=/admin so it is never sent to the public website. `AUTH_URL` must be the Auth.js address INCLUDING the path: `https://<domain>/admin/api/auth` (a mismatch makes Auth.js warn). Auth.js's own error logging is replaced with PII-free one-line events.
- Sign-in defences, in order: input shape -> 30 attempts per IP per 15 min -> lockout check (5 FAILED attempts per email + IP per 15 min; only failures count, via the limiter's peek/hit) -> Turnstile verified on the server (fails closed) -> account lookup and password check -> count a failure. An unknown email still does a full PBKDF2 check against a dummy hash so timing does not reveal which emails exist. Every failure shows one generic message; locked shows "too many attempts" whether or not the email exists. Counter keys are hashes (no email or IP in KV). Same KV caveat as the website: a coarse brake, not an exact meter.
- Passwords: PBKDF2-SHA256, 100k iterations (the workerd cap). New passwords need 10+ characters, some variety, must differ from the current one and not contain the email. Changing one needs the current password, and wrong guesses are limited to 5 per person per 15 min (a stolen session cannot guess it). A temporary password (CLI, or a manager/owner in the Team screen) sets `mustChangePassword`, which forces the change-password screen before anything else. The temporary password is shown ONCE, is never stored or logged in clear, and a reset is limited to 20 per person per hour. Owners may reset anyone but themselves; managers only receptionists and stylists of their own branch (never an equal or an owner, never themselves).
- Old sessions survive a password reset until they expire (8 h), but they are forced to the change-password screen, which needs the temporary password: so they gain nothing. Real session revocation (a `passwordChangedAt` column) is in FUTURE.md.
- No `middleware`/`proxy` is used for auth: every page and every API route checks the person itself (middleware-only auth has been bypassed before, and Next 16's Node-runtime proxy on OpenNext is unproven). Pages redirect to sign-in; the API answers 401. Every staff page and API response carries `X-Robots-Tag: noindex` and `Cache-Control: private, no-store`.
- Schedule: today view follows the branch's own clock (rolls over at the branch's midnight); calendar adds date navigation and day/week. Day = time grid with a column per stylist (a list on phones); week = seven day columns of cards. Cancelled and no-shows are hidden unless "Show cancelled and no-shows" is ticked. Polling is every ~20 s (TanStack Query); a booking is "new" if it is present now and was absent at the previous refresh of the same branch/day/view, and is marked with a "New" badge plus a screen-reader announcement (never a colour alone).
- PWA: manifest (scope and start under /admin), real PNG icons made from the placeholder monogram, maskable icon, favicon, iOS home-screen icon. Chrome reports it installable (the only complaint in a test browser is "in-incognito"). No offline mode and no service worker in v0 (booking needs a connection); the read-only offline schedule was a stretch goal and is in FUTURE.md.
- Shared code: `@salon/security` (rate limiter, Turnstile check, same-origin and client-IP helpers, Cloudflare env/KV access) and `@salon/ui/turnstile` (the widget) are used by both apps. Date and money formatting helpers are duplicated between the website and the staff app (small, but extract them if they drift).
- Linux Cloudflare build of the staff Worker: 18.2 MiB raw, 4.6 MiB gzipped (Auth.js + Prisma + the booking engine). Fits the paid plan under either reading of Cloudflare's docs. Not yet checked: that a bundle this large starts within Workers' 1-second startup limit (needs a real deploy).
- `pnpm db:create-staff -- --email ...` was broken (pnpm passes the literal `--` through and the script's argument parser then ignored every option). Fixed: it works with or without the `--`.
- Browser tests for the staff app are committed (Playwright, 19 tests, in CI): a booking made on the website appears in the right stylist's column; a receptionist at another branch is refused by every route and nothing changes; stylist limits; check-in and complete with history; cancel frees the time for the website; phone booking at an odd time through the same engine; "start right now" uses the branch clock; live "New" arrival; manager resets a colleague's password and the colleague must choose their own; lockout; cookie flags and sign-out; deactivation takes effect at once; installability; axe on every screen at desktop and phone width. They create their own accounts (emails end in @e2e.invalid) and bookings and delete them, start both apps, refuse non-local databases, and use Cloudflare's dummy Turnstile keys.
- M6, security headers: one shared builder (`packages/security/src/headers.ts`) used by both apps through `next.config.ts` `headers()`, not middleware (the brief says middleware; middleware would make the static pages dynamic and Next 16's Node-runtime proxy on OpenNext is unproven). CSP: `default-src 'self'`, scripts `'self' 'unsafe-inline'` (no nonces: static pages), Turnstile script+frame only on `/book` (website) and `/login` (staff), Cloudflare Web Analytics only on the website, `frame-ancestors 'none'`, `object-src 'none'`, `form-action 'self'`; plus nosniff, `X-Frame-Options: DENY`, strict-origin-when-cross-origin, Permissions-Policy, HSTS 1 year with includeSubDomains (no preload: that is a commitment the owner should choose). Dev adds `'unsafe-eval'` (Next's overlay). Browser tests check the headers and that the Turnstile widget works with no policy violations. Whether OpenNext applies `headers()` to prerendered pages is unproven until a real deploy.
- M6, Sentry: no SDK. A ~100-line reporter (`packages/security/src/error-report.ts`) posts to Sentry's documented envelope endpoint from Next's `onRequestError` hook (`instrumentation.ts` in both apps), because the SDK is large (the Workers bundles are already big) and its Cloudflare/OpenNext setup cannot be proven without a deploy. It sends the error class, the first message line with emails and 6+ digit runs blanked, the stack, the route pattern, the method and a database error code, nothing else; at most 20 reports a minute per isolate; does nothing without `SENTRY_DSN` (a secret). Browser-side errors are not reported. Unit-tested with personal data in the error text.
- M6, analytics: Cloudflare Web Analytics through the manual snippet (`NEXT_PUBLIC_CF_BEACON_TOKEN`, build time, off when unset), so the staff app never gets it (automatic injection would add it to every page on the zone).
- M6, uptime: `GET /api/health` (no database) and `GET /api/health?db=1` (runs `SELECT 1`, rate limited, 503 with no details). The database check is deliberately separate: on Neon Free every check wakes the database, and always-awake would exceed the monthly free compute. The uptime service is the owner's choice; UptimeRobot's free plan is, per most sources, non-commercial only (sources conflict; read their terms).
- M6, load test: autocannon 8.0.0 + a booking-contention phase (`apps/web/scripts/load-test.mjs`, `pnpm --filter @salon/web load-test`, also in CI). Findings that led to code changes: (1) the availability request cost about 31 ms of CPU, about 75% of it Luxon working out zone offsets (`partsOffset`), so `instantAt` now caches per day (immutable values; DST-tested in `time.test.ts`): 34 to 150 requests/s on one thread, p99 805 to about 220 ms; (2) the engine's three independent lookups (branch, services, candidate staff) now run together (one round trip instead of three; matters on Neon); (3) local `pg` mode shares one Prisma client (Workers still build one per request). Contention result: 30 simultaneous attempts for one stylist's slot give exactly 1 booking and 29 refusals; "any stylist" never gives more winners than stylists; the database holds exactly the confirmed bookings.
- M6, Lighthouse: `pnpm --filter @salon/web lighthouse` (Lighthouse 13.4.1 driving Playwright's Chrome; phone profile) on the 8 public pages: 92-98 performance, 100 on accessibility, best practices and SEO, with the CSP active. In CI at a 90 floor; a laptop `next start` is a guide, the live site is the real check.
- M6, backups: Neon point-in-time restore (Free 6 hours, Launch up to 7 days; checked 2026-11-02) plus a nightly encrypted export (`scripts/backup.sh`: pg_dump from the `postgres:17` image, AES-256 via openssl, `--verify` restores it into a throwaway database and checks row counts and the overlap constraint) uploaded by the `Database backup` workflow to a private R2 bucket. Never an artifact (artifacts of a public repository are public). Inert until its secrets exist.
- M6, deploys: `Deploy website` workflow (nightly + manual) rebuilds the website so expired promotions drop off. Untried against real Cloudflare. The staff app is deployed by hand on purpose. Both new workflows skip with a notice when secrets are missing.
- M6, seed guard: `db:seed` refuses any database not on localhost unless `ALLOW_PLACEHOLDER_SEED=yes` (it loads fake staff accounts).
- M6, `pnpm audit --prod` reports 3 advisories (glob, minimatch), all inside OpenNext's build tooling; recorded in SECURITY.md, to revisit when OpenNext updates.
